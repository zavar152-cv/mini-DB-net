# ZGDB Network

Клиент-серверный слой для учебной базы данных ZGDB. Консольный клиент разбирает запросы на языке ZPath, сериализует AST в XML и отправляет его по TCP; сервер преобразует XML обратно в операции над файловым ядром и возвращает структурированный ответ.

Репозиторий объединяет код двух предыдущих этапов:

- [ZGDB Core](https://github.com/zavar152-cv/mini-DB-core) — файловое хранилище и операции над документами;
- [ZPath](https://github.com/zavar152-cv/mini-DB-query-lang) — лексер, парсер и AST языка запросов.

## Архитектура

```text
ZPath-запрос
    ↓ Flex/Bison
AST на клиенте
    ↓ XML
TCP-соединение
    ↓
XML → операция ZGDB → бинарный файл БД
    ↓
XML-ответ → вывод клиента
```

Клиент и сервер обмениваются сообщениями с префиксом длины: сначала передаётся размер XML-пакета, затем его содержимое. Сервер поддерживает операции `ADD`, `FIND`, `UPDATE`, `DELETE`, `JOIN` и `PARENT`.

## Требования

- Linux или другая POSIX-совместимая система;
- CMake 3.23+;
- компилятор с поддержкой C17;
- Flex и Bison;
- libxml2.

Пример установки зависимостей в Ubuntu/Debian:

```bash
sudo apt update
sudo apt install build-essential cmake flex bison libxml2-dev
```

## Сборка

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Сборка создаёт два исполняемых файла в подкаталогах `build/zgdbServer` и `build/zpathClient`.

## Запуск

Сначала запустите сервер, передав произвольный первый аргумент и порт:

```bash
./build/zgdbServer/ZGDBProject server.zgdb 25562
```

Затем передайте тот же порт клиенту и введите один ZPath-запрос в стандартный ввод:

```bash
echo 'FIND /"users";' | ./build/zpathClient/ZPathProject 25562
```

> В текущем прототипе сервер принимает путь первым аргументом, но фактически открывает файл `/tmp/server1.zgdb`. Это известное ограничение реализации.

## Структура

```text
zgdbServer/    # TCP-сервер, ядро ZGDB и XML-десериализация
zpathClient/   # TCP-клиент, парсер ZPath и XML-сериализация
lab3report.pdf # описание проекта и экспериментов
```

## Ограничения

- POSIX-сокеты: сетевой слой не собирается на Windows без адаптации;
- сервер обслуживает клиентов последовательно;
- нет аутентификации, шифрования и ограничений размера входного сообщения;
- протокол использует нативное представление `int` для длины пакета;
- проект является учебным прототипом, а не production-сервером БД.
